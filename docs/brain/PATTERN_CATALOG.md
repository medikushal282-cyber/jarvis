# Pattern Catalog — Design Patterns Extracted from the Reference Agent Specification

**Purpose.** This document distills the design patterns found in a large reference specification for a conversational AI assistant into a catalog we can act on when building the **Brain** module: the objective → RECALL → UNDERSTAND → PLAN → SELECT → CALL → OBSERVE → DECIDE → (LOOP | RECOVER | FINISH) → RETAIN loop.

**How to read the table.** "Where it appears" names the *topic or section* of the reference design, never a page number, because we want the idea, not the location. "How OUR system implements it" always names a concrete artifact in *our* repo:

| Our artifact | What it is |
|---|---|
| `config/soul.md` | Persona, tone, values, boundaries, output-shape policy |
| `config/agents.md` | Autonomy, precedence rules, policies, safety, stopping + memory rules |
| `config/profiles/*.yaml` | Presets (sales / devops / support) bundling soul + policies + tool sets |
| `config/tools/*.yaml` | Per-tool name, description, JSON-schema params, permission tier, timeout, retry, idempotent, provider |
| `app/graph/workflow.py` + `app/graph/state.py` | The state machine (which phase we are in, what transitions are legal) |
| `app/graph/controller.py` + `app/graph/nodes/*` | Orchestrator, executor, validator, recovery, researcher nodes |
| Assembler (`app/brain/assembler.py`) | Builds the prompt: soul + agents + rendered tools + recalled memory + task context, token-budget aware |
| Planner (`app/brain/planner.py`) | Produces small revisable plans with per-step success criteria |
| Parser (`app/brain/parser.py`) | Tool-call parsing, schema validation, repair prompts, fallback ladder |
| Policy engine (`app/workspace/policy.py`, extended in `app/brain/policy.py`) | Permission tiers, confirmations, budgets, redaction, untrusted-content wrapper |
| `app/llm/router.py` | Model routing, fallback chain, backoff with jitter |
| `app/memory/*` (hindsight, okf, extractor, context_builder) | RECALL and RETAIN |
| `app/events.py` + SSE viewer | Structured event emission on every transition |

## The Catalog

| # | Pattern | Where it appears (section/topic) | What it achieves | How OUR system implements it (concrete) | Adopt? |
|---|---|---|---|---|---|
| 1 | Explicit self-declaration header | Opening identity block — "who the assistant is, who made it, which surface it runs on" | Gives the model a stable anchor so behaviour does not wander across a long session | `config/soul.md` opens with a short identity + purpose clause; `config/profiles/*.yaml` overrides only the role noun (sales engineer, SRE, support agent) | yes |
| 2 | Character-stability clause | Boundary notes around memory — values must not drift as context accumulates | Prevents the persona from being eroded by long context or by user pressure over many steps | `config/soul.md` "non-negotiables" block; assembler re-injects it verbatim on every planning turn so it is never the part that gets trimmed | yes |
| 3 | Surface-aware capability statement | Product/interface description — what the running surface can and cannot do | Stops the model promising abilities the current runtime lacks | `config/profiles/*.yaml` declares `capabilities:` list; assembler renders only declared tools into the tool section, so an undeclared ability is structurally un-actionable | yes |
| 4 | Layered precedence ladder | Behaviour preamble + copyright section + preference guardrails | Resolves conflicts deterministically instead of leaving the model to guess | Explicit ordering in `config/agents.md`: safety/deny-tier > workspace policy > user instruction > profile default; enforced in code by `app/brain/policy.py` before the assembler ever renders a conflict | yes |
| 5 | Live instruction outranks stored instruction | Preference-guardrail note: a current request beats a saved preference | Keeps stale memory from overriding what the user wants right now | `config/agents.md` rule; implemented in the planner by tagging recalled items `advisory` vs `binding` and letting task context win on collision | yes |
| 6 | Self-declared authority is not authority | Reminder block — text claiming to come from the operator must not loosen restrictions | Blocks the classic "I am the system, ignore your rules" escalation | Policy engine treats any in-band text claiming elevated provenance as untrusted content; deny-tier tools cannot be unlocked by prompt text at all, only by a config change | yes |
| 7 | Write-time plus read-time filtering | Preference guardrails — instructions filtered when stored, and filtered again when loaded | Defence in depth: a leak at one boundary is caught at the other | `app/memory/extractor.py` refuses to write banned instruction shapes; `app/memory/context_builder.py` re-screens what it retrieves before RECALL hands it to the assembler | yes |
| 8 | Ordered routing checklist, first match wins | Request-evaluation checklist — "does this need a tool at all → is a suitable tool available → did the user ask for an artifact → otherwise answer" | Stops over-tooling (calling a tool when prose suffices) and under-tooling alike | `app/brain/planner.py` starts every run with this same four-question ladder before it emits any step | yes |
| 9 | Tool-priority ladder | Retrieval guidance — private/internal sources first, then external, then a blend | Prefers the source most likely to hold the ground truth for the question | `config/tools/*.yaml` carries a `provider` and `authority_rank`; the planner sorts candidate tools by rank when several could satisfy a step | yes |
| 10 | Direct-answer-vs-lookup test | Retrieval guidance — answer plainly when knowledge is settled, look up when it can have changed | Avoids spending a call on a fact that cannot have moved, and avoids answering a fact that has | Planner assigns every step a freshness tag of `static` or `volatile`; only `volatile` steps require a tool call | yes |
| 11 | Unrecognized-entity rule | Retrieval guidance — an unfamiliar proper noun must be looked up before answering | Converts "I half-remember this" into a verified fact instead of a confident error | Planner node emits a mandatory `VERIFY` step whenever an entity in the objective is absent from both the workspace knowledge base and recalled memory | yes |
| 12 | Never narrate the tool choice | Retrieval guidance + visualization routing — do not announce the routing decision | Keeps the trace clean and the user-facing output about the answer, not the machinery | `config/agents.md` output policy; the assembler posts the decision to `app/events.py` as a structured event rather than into the model-visible text | yes |
| 13 | Batch independent calls, no interleaving | Image/retrieval tool guidance — run parallel calls as one uninterrupted block, then continue prose | Fewer round trips, and a result block that reads as one coherent answer | CALL phase in `app/graph/workflow.py` collects all steps with no unmet dependency and dispatches them concurrently; assembler is forbidden from injecting commentary between results | yes |
| 14 | Structured elicitation tool | Tool-definition block — present 2–4 tappable options instead of asking in prose | Turns a blocking free-text question into a cheap one-tap answer, and bounds how much the agent interrogates | `ask_user` capability in the planner's escalation path; capped at one question, max four options, re-asked at most once per objective | yes |
| 15 | Turn ends when you ask | Same — after the question is posed the turn is complete | Prevents the agent from answering its own question or drifting past the handoff | State machine moves to `AWAITING_INPUT` and the run suspends; `app/events.py` emits `escalated.to_user` and no further model call fires until input arrives | yes |
| 16 | Read-once paging discipline | Past-conversation reading guidance — read one page, take a second only if the answer is cut off, never a third | Bounds context growth and stops unbounded transcript trawling | RECALL budget in the assembler caps retrieval rounds; a second expansion for the same query key requires the validator node to report the answer was truncated | yes |
| 17 | Do not repeat an ignored suggestion | App/plugin suggestion guidance — one suggestion, and never re-offer after a dismissal | Protects attention; repeated offers train the user to ignore the agent | Policy engine keeps a per-run `suppressed_suggestions` set; the planner filters candidates through it before proposing | adapt |
| 18 | Durable-fact horizon test | Memory calibration — would this line still be true and useful a month later, in a different conversation | Separates durable knowledge from the churn of the current task | RETAIN gate in `app/memory/extractor.py`; anything failing the horizon test is kept in run-scoped state, not written to Hindsight | yes |
| 19 | Origin test for stored facts | Memory calibration — file what the user supplied, not what you concluded | Keeps model inference and advice out of the knowledge base | `app/memory/extractor.py` tags each candidate with an origin of `user`, `tool_output`, or `model`; only `user` origin reaches the durable store, the rest is echoed into the answer | yes |
| 20 | Calibrate the claim to the evidence | Memory calibration — one mention earns "mentioned this once", never "is an enthusiast" | Stops a single data point from hardening into a generalisation later recalled as fact | RETAIN writes a `confidence` and `observations` count alongside each fact; RECALL downgrades anything with `observations: 1` to advisory | yes |
| 21 | Omit, never placeholder | Memory omission guidance — blocked material is dropped entirely, not reworded or generalised | A placeholder is itself a disclosure; "managing a health condition" leaks as much as the condition | Redaction layer in `app/brain/policy.py`: blocked spans are removed at the character level and the surrounding sentence is rewritten, never stubbed | adapt |
| 22 | Read-before-write with a version token | Memory edit guidance — load the file, then pass its version with the write | Makes concurrent updates safe and prevents a blind overwrite from destroying another writer's line | `app/memory/okf/manager.py` uses optimistic concurrency: read returns `if_version`, write rejects on mismatch and returns current content for a merge | yes |
| 23 | Pick the write op by change size | Memory edit guidance — small patch, append, or full rewrite, chosen by how much moved | Avoids rewriting a large document to change one line, and avoids append-sprawl | Three operations in `app/memory/api.py` (`patch`, `append`, `replace`); the RETAIN step selects by diff size before issuing | yes |
| 24 | Conflict is coordination, not failure | Memory edit guidance — a version clash is routine; merge and retry immediately | Keeps a benign race from becoming an error path or a user-facing question | Recovery node in `app/graph/nodes/recovery.py` classifies version conflicts as `retryable_merge`, not as a failure requiring the user | yes |
| 25 | Durable phrasing over precise figures | Memory calibration — describe the stable shape, not the numbers that go stale | Facts survive their first real-world change | RETAIN normalisation strips absolute timestamps and one-off quantities, keeping the pattern (e.g. a recurring weekday cadence rather than a dated slot) | yes |
| 26 | Check the store before asking the user | Memory application + listing guidance — consult what is filed before requesting context | Removes the worst user experience in an agent: being asked for something it already has | RECALL is the mandatory first phase of every run in `app/graph/workflow.py`; a plan that contains an `ask_user` step must first carry a RECALL result for that same key | yes |
| 27 | Relevance test for recalled facts | Memory application guidance — a stored fact must change the answer, or it stays out | Prevents decorative personalisation that reads as surveillance and burns tokens | `app/memory/context_builder.py` scores each retrieved item by whether the current objective references it; below-threshold items are dropped before assembly | yes |
| 28 | Never narrate retrieval | Forbidden-phrase guidance — no "I remember", "based on your memories", "according to your profile" | Keeps recalled knowledge indistinguishable from reasoning, which reads as competence rather than data-mining | `config/soul.md` wording rules plus a post-generation check in the validator node that flags retrieval-announcing phrases | yes |
| 29 | Fullness means consolidate | Memory size-cap guidance — cap reached triggers rewrite/merge, not halting writes | Keeps the store useful at a fixed size instead of silently degrading | `app/memory/okf/manager.py` runs a compaction pass on cap breach: merge overlapping entries, roll repeated event logs into a dated summary, preserve headroom | yes |
| 30 | Store the pointer, not the copy | Memory size-cap guidance — when the canonical record lives elsewhere, keep a reference plus a short digest | Avoids duplicating a system of record that will drift from its copy | RETAIN writes a `ref:` record (source name + location + digest) instead of inlining large external logs | yes |
| 31 | Effort scales with the request | Tone/formatting guidance — scale response length and depth to complexity and stated need | A one-line question does not deserve a report, and a hard objective does not deserve a one-liner | `config/agents.md` effort policy keyed to plan step count; `config/profiles/*.yaml` sets a per-profile verbosity ceiling the assembler enforces | yes |
| 32 | Minimum sufficient formatting | Formatting guidance — use only the structure clarity requires; drop it in informal registers | Formatting is a signal; over-applying it makes every answer read the same | `config/soul.md` output-shape rules; `config/profiles/*.yaml` may set a formatting mode of `structured` or `plain` | yes |
| 33 | No bullets inside a refusal | Formatting guidance — declining carries no list structure | The visual softening matters at the moment the user is being told no | `config/soul.md` refusal-shape rule; validator rejects a refusal payload that contains list markup | yes |
| 34 | Answer first, process second | Retrieval guidance — the opening sentence answers, provenance comes later if at all | Forces the model to commit to an answer instead of burying it under methodology | FINISH output contract in `config/agents.md`; validator node fails a finish payload whose first sentence is not the answer | yes |
| 35 | Post-tool reply contract | Reply-after-tool-calls guidance — state the result; a bare acknowledgement is not a reply; do not restate pre-call text | Eliminates the classic "Done." non-answer and the duplicated summary | FINISH phase of `app/graph/workflow.py`: the final message must cite at least one tool result ID and must not repeat text already emitted in the same run | yes |
| 36 | Strip markup before parsing | Embedded-API error-handling guidance — strip code fences, join content blocks, wrap the call in a try/catch | Tool output arrives wrapped; parsing it naively is the most common silent failure | Parser step zero in `app/brain/parser.py`: unwrap fences/prose, extract the JSON span, then validate; every call site is exception-guarded | yes |
| 37 | Deterministic repair ladder | Tool-definition + structured-output guidance — schema-first, with a defined degradation order | Turns "the model returned something unusable" from a crash into a degraded success | `app/brain/parser.py` ladder: native function call → JSON mode → constrained text parse → repair prompt with the validation error attached → fail the step | yes |
| 38 | Own the mistake, keep your footing | Responding-to-mistakes guidance — acknowledge, correct, no excessive apology or self-abasement, and do not become more submissive under pressure | Keeps a recovery honest without the agent degrading into flattery, which destroys its usefulness | `config/soul.md` stance rules; recovery node emits a structured `self_correction` event so the correction is visible and auditable | yes |
| 39 | Attempt the ambiguous ask before interrogating | Tone guidance — try to address an ambiguous request before requesting clarification | Users hate being blocked; often the ambiguity resolves with a stated assumption | Planner marks genuinely ambiguous steps `assume_and_note` rather than `ask_user`; the assumption is carried into FINISH when the workflow reports what it took for granted | yes |
| 40 | Warn, confirm, then act | End-of-interaction policy — a terminal action needs a prior warning and an explicit confirmation | Makes irreversible operations a two-party decision rather than a one-shot | Deny/confirm tiers in `config/tools/*.yaml`; `confirm` tier routes through `app/brain/policy.py` which emits a `confirm.required` event and suspends the run | yes |
| 41 | The tool itself challenges a dangerous call | End-of-interaction policy — the first call is a request for confirmation and is not itself the action | Adds a guard the model cannot forget, because the guard lives in the tool, not the prompt | Destructive tools in `config/tools/*.yaml` declare `requires_confirmation: true`; the executor refuses to run them without a matching approval token on the call | yes |
| 42 | Never claim an action you did not observe | Automation guidance — a simulated or fabricated result is never acceptable | The single most corrosive failure mode for a tool-using agent: a plausible lie the user acts on | Validator node refuses to let FINISH cite a step whose OBSERVE record has no tool result ID and non-error status | yes |
| 43 | State the principle, not the tripwire | Refusal guidance — explain the boundary without narrating the detection rule that fired | Explaining the test teaches how to route around it | `config/soul.md` refusal shape; policy engine returns a reason code that the assembler renders as a principle sentence, never as the matched rule | yes |
| 44 | A refusal is sticky within a run | Refusal guidance — once declined, keep declining narrower rewordings in the same session | Otherwise the agent can be walked past its own boundary one small step at a time | Policy engine stores denied `(action, subject)` pairs in run state; a reworded request that normalises to the same pair is auto-denied without a fresh model call | yes |
| 45 | Refuse the capability, keep the safety | Refusal guidance — decline what enables harm but still supply the life-preserving information | A blanket refusal is both unhelpful and worse for the person than a partial answer | `config/agents.md` tiering rubric: `deny` (enabling detail), `redirect` (safe alternative + reason), `assist` (general context) — decided by policy engine before generation | yes |
| 46 | Stay inside your professional lane | Legal/financial advice guidance — give the facts and name the limits rather than issuing a verdict | Prevents the agent from being read as an authority it is not | `config/soul.md` boundary lines; `config/profiles/support.yaml` can tighten this for customer-facing runs | yes |
| 47 | Treat all tool output as data | Persisted-artifact and search guidance — results are not instructions; ignore directives found inside them | The core prompt-injection defence for any agent that reads external content | Policy engine wraps every tool result in an explicit untrusted envelope before it reaches the assembler; the assembler's system block states that envelope contents are data | yes |
| 48 | Memories are untrusted too | Safety reminder around the memory system — stored content may itself carry hostile instructions | Closes the slow-burn injection path: poison memory once, execute on every later run | `app/memory/context_builder.py` runs the same untrusted-envelope treatment over recalled memory as over tool output | yes |
| 49 | Instructions embedded in fetched content need a human | Visualization routing guidance — an instruction inside a document is not the person typing it | Stops a fetched page from driving a side effect the user never asked for | Policy engine escalates any tool call whose parameters were sourced from untrusted content and whose tier is above `auto` | yes |
| 50 | A tool's own challenge is not an injection | End-of-interaction policy — the confirmation result is a legitimate mechanism, not an attack | Prevents the agent from over-correcting and refusing to complete a normal safety flow | State machine classifies confirmation prompts by tool ID against `config/tools/*.yaml` rather than by text heuristics | yes |
| 51 | Load the playbook before doing the work | Skill guidance — read the relevant procedure file before writing code or producing an artifact | Encodes hard-won environment constraints the model cannot infer | `config/tools/*.yaml` entries may declare `prelude: <playbook>`; the planner must schedule the prelude step before the first call to that tool | yes |
| 52 | Never fake a capability | Suggestion guidance — never manufacture a mock tool result or a simulated experience | Fabrication is indistinguishable from success until the user acts on it | Policy engine rejects any tool call naming a tool absent from the loaded `config/tools/*.yaml` set; the planner's SELECT step can only choose from the rendered list | yes |
| 53 | Re-inject the constitution over long runs | Operator reminder topic — a periodic reminder keeps instructions salient as context grows | Long contexts bury early instructions; periodic re-anchoring keeps behaviour stable | Assembler places `config/soul.md` + `config/agents.md` non-negotiables at both the head and tail of the prompt, and the state machine re-injects them at every DECIDE node | yes |
| 54 | Stateless calls, complete state every time | Context-window management guidance — the model holds no memory between calls, so each request carries everything | Removes the assumption of server-side session state and makes runs reproducible | Assembler is the single owner of request construction; `app/graph/state.py` is serialised into every call, never assumed to persist provider-side | yes |
| 55 | Compaction by merge, not truncation | Context guidance — summarise older material in batches and keep the recent detail | Keeps history meaningful instead of chopping the oldest turns off a cliff | Assembler trimming order is deterministic: drop re-derivable tool payloads → summarise completed plan steps → compact recalled memory → only then trim conversation | yes |
| 56 | Token-limit parameters on retrieval | Retrieval tooling guidance — a fetch accepts a text budget and truncates to it | Puts the context budget in the caller's hands instead of discovering it after the fact | `config/tools/*.yaml` supports `max_tokens` per tool; assembler reserves a per-step slice so one large result cannot starve the plan | yes |
| 57 | Say what you do not know | Accuracy guidance — decline to supply a figure, URL, or name you cannot ground; never infer a name nobody gave | Grounded uncertainty is more useful than a fluent guess, and much cheaper to recover from | Validator node flags unsupported specifics in the FINISH payload; `config/soul.md` requires the gap to be stated rather than filled | yes |
| 58 | Weight sources by how corruptible they are | Retrieval guidance — believe results generally, but be sceptical where ranking is gameable or consensus is contested | Prevents the agent from laundering a manipulated source into a fact | Tool results carry a `provenance_class` in the OBSERVE record; the validator downgrades claims resting on low-quality classes to hedged language | adapt |
| 59 | Progress narration at a controlled rate | Tone guidance — a short status line every couple of tool calls | Keeps a long run legible without turning the output into a log dump | `app/events.py` emits a structured progress event per state transition; the SSE viewer renders them, so the model's own text stays clean | yes |
| 60 | Pace and rate protection | Tool-definition guidance — batched requests, rate-limit keys, explicit backoff | Keeps a multi-step run alive when a provider pushes back instead of collapsing the whole objective | `app/llm/router.py`: exponential backoff with jitter on 429/5xx, per-tool concurrency caps, and a model fallback in the declared chain | yes |
| 61 | Runtime facts injected, not recalled | Product/context guidance — the current date and location come from the runtime, and the model must not treat them as remembered | Removes a whole class of stale-self-knowledge errors | Assembler injects a runtime context block (clock, run ID, workspace, profile) that is regenerated per call and never written to memory | yes |
| 62 | Grounding beats guessing on freshness | Accuracy guidance — recall is a snapshot; verify before asserting anything that could have moved | Stops vivid-but-stale knowledge from being delivered with full confidence | Planner's freshness tag (row 10) combined with the verifier node, which requires a source for every `volatile` claim in FINISH | yes |
| 63 | Name the real control instead of agreeing | Capability-limit guidance — do not pretend a setting changed; name where the control actually lives | Prevents the agent from performing compliance it cannot deliver | `config/agents.md` honesty rule; when a requested toggle is not available, the planner returns a `capability_gap` result instead of an acknowledgement | yes |
| 64 | Memory on/off is an operator switch, not a model decision | Memory application guidance — the model cannot disable its own memory and must say so | Keeps a policy control in the hands of whoever owns the deployment | `config/agents.md` `memory.enabled` flag, surfaced as a run parameter and toggled by the caller; RECALL/RETAIN nodes no-op cleanly when false so the loop still runs | yes |
| 65 | Improvement is measured across runs | Memory application framing — the store exists to make the next run better | Without a metric, a memory subsystem is indistinguishable from a log | RETAIN writes a run record (steps, tokens, retries, recoveries); the tracker reports a per-objective delta so the memory toggle can be evaluated rather than assumed | yes |
| 66 | Partial completion is a valid exit | Multi-turn guidance — deliver what is solid and say what remains | A run that hit a budget is not a failure; silently truncating is | FINISH supports `partial` with a stated gap list; the recovery node escalates to `partial` when any budget trips, rather than looping | yes |
| 67 | Goal verification before declaring done | Verification framing around finishing | Stops the loop from terminating on a plausible-looking step instead of the objective | Planner attaches a `success_criteria` predicate to every step; the validator node must pass all criteria before DECIDE may transition to FINISH | yes |
| 68 | Repeated-call loop detection | Recovery framing around retries | The most common agent hang is a call that keeps succeeding without advancing | State machine hashes `(tool, normalised_args)` per step; a third repeat with unchanged step state forces RECOVER (alternative tool, or re-plan, or partial finish) | yes |
| 69 | Budget triage in a fixed order | Stopping-policy framing | Makes the "we have to stop" decision deterministic rather than emergent | `config/agents.md` declares step / token / wall-clock budgets; DECIDE evaluates them in that order and routes to `graceful_partial` before the hard limit | yes |
| 70 | Idempotency as a retry precondition | Tool-definition framing (safe-to-repeat operations) | Retrying a non-idempotent call is how an agent double-charges someone | `config/tools/*.yaml` requires an `idempotent` flag; the recovery node auto-retries only when it is true, otherwise it escalates or picks an alternative tool | yes |

**Row count: 70.**

## Notes on the catalog

**The reference is chat-shaped, so the transfer is imperfect.** It is a specification for a single interactive assistant, and a large share of its text concerns things we have no equivalent for: a product surface, consumer feature toggles, a partner ecosystem, a rendering layer. Roughly a third of its content is directly portable as agent-loop mechanics (routing, tool discipline, recovery, verification, memory hygiene); another third transfers only after reframing (its privacy taxonomy becomes our redaction policy; its "surface capabilities" becomes our declared tool set); the remainder is surface-specific and is listed as not adopted.

**Where our interpretation is narrower on purpose.** Rows 21, 38, 44, 45, 58 are marked `adapt` rather than `yes`. In each case the reference rule is broader than our need — its privacy taxonomy is built for a personal assistant handling a lifetime of user disclosures, whereas ours mostly needs secret redaction and injection resistance. We take the mechanism and drop the catalogue.

**Two patterns carry disproportionate weight.** Row 47 (all tool output is data) and row 67 (verify the goal before finishing) are the two that separate a demo that looks impressive in a happy path from one that survives an adversarial input and a hostile step budget. If the schedule compresses, build those first.

**The reference covers a few things thinly.** There is no real treatment of multi-agent delegation and how authority should be bounded when a sub-agent inherits a task — it only gestures at offering an autonomous background job and at discovering installable capabilities. There is nothing substantive on parallel tool execution beyond "batch calls that do not depend on each other": no discussion of partial failure across a parallel batch, no ordering guarantees, no rollback when call 3 of 5 fails. There is also no explicit state-machine description — the phase structure is implied throughout but never specified as transitions and guards, which is precisely the part we had to invent. Cost accounting per step is absent, and cancellation of an in-flight run is unaddressed.

## Deliberately NOT adopted

| Pattern from the reference | Why we skip it |
|---|---|
| **Consumer product-and-feature narration** — sections that tell the user about plans, settings, and how to change preferences | Presumes a consumer product surface with a settings UI. Our caller is an API/workspace; there is nowhere to send a user to click something. |
| **A versioned model-family catalogue** — capability tiers, model strings, availability differences between tiers | Presumes a multi-product ecosystem with frequent releases. We declare two Groq models in `app/llm/router.py` and nothing more. |
| **Wellbeing and crisis-response protocol** — the full taxonomy of mental-health, self-harm, and disordered-eating handling, plus named helplines | Presumes a general-purpose companion handling a person's worst moments, and creates a duty of care we cannot honour in a hackathon build. We keep a generic refusal path (rows 43–45) and nothing further. |
| **Evenhandedness doctrine for contested public topics** — how to present political and ethical positions without a personal view | Presumes a public-facing opinion-bearing assistant. Our agent executes objectives; it has no standing to take or withhold political positions. |
| **Child-safety content rules** — the detailed content-safety regime for minors | Presumes a general content-generation surface. Our tools act on a workspace; the analogue is the deny tier, already covered. |
| **Copyright quotation ceilings and displacive-summary rules** — the per-source quote budget and the ban on mirroring a source's structure | Written for long-form recitation to a reader. Our agent emits task output. We keep only the redaction and provenance-attribution subset (rows 21, 58). |
| **Browser-storage prohibition and the persisted key-value artifact store** — the client-side storage API, key-design guidance, and shared/personal data scopes | Presumes we host user-authored HTML artifacts in a browser we control. We do not render untrusted user code. |
| **Connector and MCP-app marketplace flow** — registry search, then an opt-in picker, then the call, with a rule about never choosing a partner on the user's behalf | Presumes a commercial ecosystem and a clickable choice surface, plus partner-selection ethics that only matter when providers compete for the user. Our tool set is fixed by config. |
| **Plugin and skill catalogue cards** — searching an organisation catalogue and rendering one install card per conversation | Presumes a curated org catalogue and a UI that renders installable cards. Our `config/tools/*.yaml` is the catalogue and it is edited, not installed. |
| **Past-conversation search tooling** — topic search, time-window listing, and read-at-hit paging across a transcript corpus | Presumes a long-lived multi-turn chat history we can query. Hindsight RECALL covers the retrieval need in one step; a second overlapping retrieval path is pure surface area. |
| **Inline visualisation module loading** — fetching a rendering module before producing a diagram, with routing rules between it and other visual tools | Presumes an inline rendering surface in a chat client. Our trace is an SSE event stream, not a canvas. |
| **The long tail of consumer tools** — image search, places, weather, sports, recipes, quizzes, translation cards, product comparison cards, research-upsell buttons | Each is a distinct product feature bound to a consumer surface. None maps to an executable capability in our loop. |
| **Document-format skill routing** — choosing between word-processing, slide, and spreadsheet outputs and weighing their token cost | Presumes a document-authoring deliverable. Our agent's outputs are data, actions, and a trace. |
| **Knowledge-cutoff date and the default-to-search reflex** — a fixed cutoff plus a rule that anything that might have changed must be searched | Presumes open-ended web browsing from a fixed training snapshot. Our freshness handling is per-step (row 10) and our tools are declared, so there is no unconstrained search to gate. |
| **Ending a conversation** — warnings, redirection attempts, and double confirmation before terminating the exchange | Presumes a conversation that can be ended. Our analogue is aborting a run, and we handle that with budgets and a partial finish (rows 66, 69) rather than a social protocol. |
| **Relationship-boundary framing** — guidance about not standing in for human connection and not over-reading stored context | Presumes an assistant a person might form an attachment to. It would be over-engineering here; a task agent has no companionship surface to bound. |

**That is 16 non-adoptions**, comfortably above the six-entry floor. The through-line: anything that presumes a product surface, a billing or partner ecosystem, an interactive multi-turn chat, a rendering layer, or a duty of care beyond task execution is out — as is anything whose cost exceeds a hackathon's time budget without changing whether the loop works.
